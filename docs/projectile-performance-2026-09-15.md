# 대량 투사체 성능 최적화 — 2026-09-16

진단(부록 A)에서 확인한 네 병목을 순서대로 개선하고, 같은 조건으로 전후를 측정했다.
적·투사체 수, 피해량, 공격 속도, 관통 횟수는 줄이지 않았다.
작업 중 발견한 **보이지 않는 적 탄환에 맞는 버그**도 함께 고쳤다(6장).

## 요약

| 확인된 병목 | 개선 전 | 개선 후 |
|---|---:|---:|
| 적 620 분산, 투사체 1,000개 한 틱 | 평균 19.2ms · p99 27.8ms | **평균 8.4ms · p99 14.7ms** |
| 투사체 1,000개 동시 표적 재탐색 틱 | 평균 157ms · p99 225ms | **평균 10.0ms · p99 15.4ms** |
| 투사체 1,000개 렌더링 (분리 측정) | 7,500 draw calls · 16.0ms | **2 draw calls · 2.4ms** |
| 투사체 2,000개 일괄 반납 (무작위 순서) | 평균 35.0ms | **평균 2.3ms** |

실제 게임 화면(적 620, HUD, 비행 높이·그림자 포함, 1920×1080)에서는 투사체 2,000개의 화면 프레임이
**평균 623ms → 15.7ms**, draw call이 **20,803 → 410**이 되었다.

## 1. 변경 내용

### 1-1. 충돌 후보 조회 — `EnemySpatialGrid.projectile_contacts()`

- 적 그리드 재구축 때 투사체 전용 **48px 조밀 격자**를 함께 만든다. 셀마다 첫 적 인덱스, 적마다 다음 인덱스를
  담는 정수 배열 두 개와 행별 적 수뿐이다. 딕셔너리 조회와 조회마다의 배열 할당이 없다.
- 탄환은 **남은 명중 수만큼만** 후보를 모으고 멈춘다. 단발 탄환은 첫 접촉에서 조회를 끝낸다.
- 명중 이력(`hit_enemy_ids`)은 조회 안에서 인스턴스 ID 평면 배열로 걸러 노드에 접근하지 않는다. 관통 탄환이 같은 적을 두 번
  때리지 않는 규칙과 관통 횟수는 그대로다.
- 판정은 이번 틱의 **이동 선분 전체**와 한다(스윕). 한 틱에 적 폭보다 멀리 가는 빠른 탄환이 적을 통과하던 문제가 사라졌다.
- 판정 반경은 **적 각자의 반지름**을 쓴다. 기존의 고정 `반경+32` 조회는 반지름이 큰 적의 가장자리를 놓쳤다.
- 거리 계산은 노드 위치 대신 `separate()`가 갱신하는 평면 위치 배열로 한다. 노드 속성 읽기가 조회 비용의 대부분이었다.
  재구축 후 군중 분리로 셀을 넘은 적은 8px 여유로 찾는다. 같은 틱 안에 무기가 끌고 간 적(중력장)은 다음 재구축부터 반영된다.
- 조회 결과는 탄환 전체가 정적 버퍼 하나를 재사용한다.

### 1-2. 표적 재탐색 — `EnemySpatialGrid.nearest()` 와 틱당 예산

- 조밀 격자에서 **원점 셀부터 고리 단위로** 넓혀 가며, 지금까지 찾은 가장 가까운 적이
  아직 보지 않은 영역까지의 최소 거리보다 가까우면 즉시 끝낸다. 빈 행은 행별 적 수로 건너뛴다.
- 결과는 기존과 같은 "반경 안의 가장 가까운 살아 있는 적"이다. 거리가 정확히 같으면 인덱스가 낮은 적을 고른다.
  무작위 군중 2,000회 대조에서 무차별 탐색과 모두 일치했다.
- 틱당 재탐색은 **640회로 제한**한다(`HomingProjectile.RETARGET_BUDGET`). 나머지는 직진하다가 다음 틱에 찾는다.
  반경 안에 적이 없으면 3틱 뒤에 다시 찾는다. 이 제한은 대량 사망 직후 한 틱에 몰리는 비용을 나누기 위한 것이다.
- 측정된 유도 반응 지연(모든 표적이 한 번에 사라진 뒤 전원 재획득까지): 500개 0틱, 1,000개 최대 1틱(16.7ms),
  2,000개 최대 3틱(50ms). 640개 이하는 지연이 없다.

### 1-3. 플레이어 투사체 배치 렌더링 — `ProjectileRenderer`

- star/ember/bolt 본체와 글로우를 각각 **MultiMesh 하나**로 그린다(본체 1회 + 가산 글로우 1회).
- 아틀라스는 손으로 다시 그린 것이 아니다. `HomingProjectile`의 그리기 코드를 정적 페인터로 분리해,
  노드 그리기와 아틀라스 굽기가 **같은 함수**를 쓴다. 색 계열(기본/뜨거운 중심/불꽃 꼬리, 글로우 원 두 개)마다
  마스크를 굽고, 셰이더가 인스턴스 색으로 원래 합성을 재현한다. 같은 색 조각의 알파 합성은 마스크 하나로 정확히 표현된다.
- 탄마다의 시드 변형은 16가지로 굽는다. 회전·크기·페이드 알파·비행 높이는 인스턴스 변환과 색으로 유지된다.
- **그리기 순서**: 탄환은 생성 순서(= 자식 순서)대로 배치되어 원래 노드 순서와 같다. 렌더러는 컨트롤러의 첫 자식이라,
  나중에 추가되는 일시 효과가 탄환 위에 그려지던 관계도 같다. 글로우는 원래 GlowLayer처럼 본체보다 z가 한 단계 낮다.
- **비행 그림자**: 실제 게임에서는 homing/flame 탄환마다 `FlightField`가 원 세 개짜리 그림자를 매 프레임 다시
  테셀레이션했고, 실제 화면 부하의 대부분이 여기서 나왔다(분리 렌더 측정에는 높이가 없어 드러나지 않았다).
  같은 방식으로 원 세 개를 채널 마스크 하나로 묶어 `draw_multimesh` 한 번으로 그린다. z 순서는 그대로다.
- 탄환의 위치·방향·크기는 노드에 변환 하나로 기록한다(속성 세 번 → 한 번). 기존 회전/크기 경로와 행렬이 같음을 확인했다.
- 비교용 토글: `WeaponController.set_batching(false)`, `FlightField.batched = false`.

### 1-4. 오브젝트 풀 반납

- 탄환이 활성 목록의 자기 인덱스를 들고 있어 반납은 **swap-remove**(O(1))다.
  `erase()`의 선형 탐색·배열 이동과 `not in projectile_pool` 전체 탐색이 사라졌다.
- 풀 포함 여부는 `in_pool` 플래그로 확인한다. 중복 반납은 `release()`의 `active` 검사와 플래그로 막는다.
- 활성 목록 순서는 반납 때 바뀌므로, 렌더러는 생성 순서 목록(`all_projectiles`)을 따로 순회한다.
  `clear_transients()`는 복사본을 순회해 순회 중 반납이 누락되지 않는다.

## 2. 측정 방법

- 같은 벤치마크 스크립트를 **개선 전 스냅숏과 개선 후 작업 트리**에서 순차 실행했다. 기능 유무는 스크립트가 감지한다.
- 표본 수를 늘렸다. CPU 분산 조건은 워밍업 30 + 측정 300, 밀집 조건은 6 + 60, 풀은 크기별 20회 반복,
  통합은 600 물리 틱, 렌더링은 워밍업 60 + 측정 600 프레임이다. 300표본의 p99는 세 번째로 느린 값이다.
- **CPU 처리 시간**과 **물리 틱 간격**, **렌더링 프레임 간격**을 따로 기록했다. 틱 CPU는 처리 우선순위 양 끝에 둔 탐침 노드
  두 개가 그 틱의 콜백 구간을 잰 값이다. `Performance.TIME_*` 모니터는 틱별 값이 아니어서 쓰지 않았다.
- 통합·실제 화면 측정은 레벨업 화면이 트리를 멈추지 않도록 막고, 멈춘 프레임이 있으면 실패로 처리한다.
- 반납 측정은 탄환을 무작위 순서로 반납한다. 앞에서부터 반납하는 경우는 기존 구현의 최선 경우였다.
- 환경: Godot 4.7.2 Steam, Ryzen 7 7800X3D, RTX 5060 Ti, OpenGL Compatibility. 측정 내내 Godot 에디터가 열려 있었다(전후 공통).
  실제 화면 측정은 저장된 창 설정 때문에 1920×1080이다(전후 공통). 릴리스 export나 다른 PC의 결과를 보장하지 않는다.

## 4. 실제 게임 장면 통합 측정 (헤드리스, 600 물리 틱)

적 620마리, 실제 적 AI·군중 분리·투사체 콜백·명중 피드백이 모두 실행된다. GPU 렌더링은 포함하지 않는다.

| 합성 투사체 | 틱 간격 전 (평균/p99/최대) | 틱 간격 후 | 물리 CPU 전 (평균/p99) | 물리 CPU 후 | process CPU 후 (평균/p99) |
|---:|---:|---:|---:|---:|---:|
| 0 | 16.65 / 20.71 / 26.35 | 16.66 / 20.72 / 21.13 | 3.50 / 5.36 | 3.75 / 5.81 | 0.54 / 1.93 |
| 500 | 33.21 / 51.54 / 64.03 | **18.15 / 28.27 / 33.03** | 31.49 / 49.77 | 15.81 / 26.33 | 1.68 / 3.19 |
| 1,000 | 61.39 / 94.61 / 114 | **29.28 / 40.56 / 50.03** | 59.53 / 89.79 | 27.33 / 38.30 | 2.65 / 3.34 |
| 2,000 | 117 / 167 / 196 | **52.40 / 72.62 / 88.13** | 115 / 165 | 50.23 / 70.37 | 4.02 / 4.94 |
| 2,000, 1초마다 전원 반납·재생성 | 103 / 184 / 223 | 55.23 / 104 / 131 | 100 / 181 | 52.57 / 93.89 | 4.07 / 6.75 |

- 물리 CPU는 적 AI 등 게임 전체 틱이며, 틱 간격에는 60Hz 대기와 밀린 틱 처리가 포함된다. 틱 간격이 CPU보다 크면 대기, 비슷하면 CPU가 한계라는 뜻이다.
- 이 조건의 탄환은 긴 수명과 큰 관통을 가져 매 틱 새 적과 계속 접촉하고, 명중마다 피해 숫자·파티클이 생긴다.
  2,000개에서 남은 50ms는 대부분 명중 처리와 피드백이며, 실제 무기의 발사량을 재현한 조건은 아니다.
- process CPU(후)에는 배치 렌더러의 버퍼 채우기가 포함된다(2,000개 약 2.5ms). 일괄 반납·재생성 2,000개는 50.5ms → 24.1ms.

## 7. 동작 변화와 주의점

- **스윕 판정**: 60Hz에서는 한 틱 이동이 적 폭보다 작아 체감 차이가 없다. 20배속 소크 테스트에서는 한 틱에 약 160px를 이동해,

- **배치 아틀라스**: 반지름 8과 9를 굽고 다른 반지름은 가까운 쪽을 확대한다. 시드 변형은 16단계다.
- **적 탄환 층**: 이제 고양이 위에 그려진다. 위협을 먼저 읽게 하려는 의도다.

## 2. 투사체 CPU 분리 측정

아래 시간은 **투사체 전체를 한 번 갱신한 시간**이다. 전체 게임 프레임 시간이나 GPU 시간이 아니다.

|---|---:|---:|---:|---:|
| 적 없음, 비유도 이동 | 0.26ms | 1.11ms | 2.32ms | 4.23ms |
| 적 620마리 분산, 기존 표적 유지 | 1.77ms | 9.62ms | 20.13ms | 38.44ms |
| 적 620마리 분산, 전 탄환 표적 재탐색 | 17.92ms | 82.30ms | 159.53ms | 310.66ms |
| 적 620마리 밀집, 한 번 명중 후 반납 | 17.92ms | 93.43ms | 194.67ms | 425.35ms |

### 조건의 의미

- 분산: 적을 1120×560 영역에 배치하고 탄환도 같은 영역에 분산했다.
- 밀집: 적 620마리를 반지름 28px에 배치하고 모든 탄환을 중심에 둔다.
  군중 분리를 실행하지 않는 **극단적인 겹침 조건**이며 평상시 전투를 뜻하지 않는다.
- 반복 가능한 부하를 유지하기 위해 매 샘플 전에 탄환 위치와 명중 이력을 복구한다.
  복구 비용은 CPU 본 측정에서 제외된다.
- 표적 유지/재탐색 조건의 탄환은 긴 수명과 큰 관통 횟수, 피해 0을 사용한다.
  적의 실제 `take_damage()`는 실행하지만 게임 장면의 피해 피드백 리스너는 연결하지 않는다.
- 재탐색 조건은 매 샘플 전에 표적을 없앤다. 대량 표적 사망 직후 **한 틱에 몰릴 수 있는 비용**을
  반복 측정한 것이며, 실제 플레이 내내 모든 탄환이 매 틱 재탐색한다는 뜻이 아니다.
- 한 번 명중 조건은 실제 컨트롤러의 풀로 반납한다. 다음 샘플의 재획득은 측정 밖에서 수행한다.

### 확인한 병목

**충돌 후보 조회:** 분산 1,000개 계측 패스는 총 19.60ms 중 `query_radius()`가 13.35ms였다.
탄환당 반환된 적은 약 5마리지만, 192px 셀 안의 다른 적들도 거리 검사를 받는다.
`scripts/systems/enemy_spatial_grid.gd:124`에서 매 조회마다 결과 배열을 구성한다.

**불필요한 전체 결과 생성:** 밀집 단발 1,000개는 본 측정 194.67ms였다.
별도 계측 총 201.48ms 중 조회가 182.14ms였다. 한 번 명중하면 사라지는 탄환도
충돌 루프에 들어가기 전에 620개짜리 후보 배열을 모두 만든다.

**동시 재탐색:** 분산 1,000개 재탐색 계측 총 158.28ms 중 `nearest()`가 136.43ms였다.
`projectile.gd:156`의 검색 반경은 900px이고, `enemy_spatial_grid.gd:143`은 그 범위의
셀을 모두 훑는다. 가까운 적을 찾았다는 이유로 셀 순회가 일찍 끝나지 않는다.

별도 극한 관통 조건에서는 한 탄환이 같은 틱에 최대 620개 명중을 처리했다.
1,000개 기준 780.97ms, 2,000개 기준 1560.06ms였다. 이는 최대 약 124만 건의
반복 명중을 강제한 상한 스트레스이며, 일반 탄환 결과와 섞어 해석하면 안 된다.

## 3. 실제 게임 장면 통합 측정

`main.tscn`을 시작하고 적 620마리와 합성 투사체를 유지했다. 적 AI, 군중 분리,
실제 투사체 네이티브 물리 콜백, 피해 숫자/파티클/소리 보고 경로가 실행된다.
헤드리스이므로 GPU 렌더링은 포함하지 않는다.

| 추가 합성 투사체 | 실제 활성 탄환 범위 | 물리 틱 간격 평균 | p99 |
|---|---:|---:|---:|
| 0 | 0–1 | 16.67ms | 20.70ms |
| 500 | 500–501 | 24.96ms | 38.20ms |
| 1,000 | 1,000–1,001 | 47.35ms | 71.58ms |
| 2,000 | 2,000–2,001 | 84.47ms | 139.77ms |

이 표는 `physics_frame` 사이의 실제 경과 시간이다. 60Hz 대기와 엔진의 밀린 틱 처리,
테스트의 탄환 위치 복구 비용을 포함하므로 CPU 함수 시간이나 화면 FPS로 읽으면 안 된다.
0개 조건의 16.67ms도 CPU가 그만큼 일했다는 뜻이 아니다.

적은 기본 chaser 620마리이며 움직여서 점점 모인다. 적/플레이어 체력은 매우 높게 두고,
탄환은 피해 0.1, 긴 수명과 큰 관통 횟수를 사용해 개수를 유지한다. 이력은 지우지 않으므로
각 탄환은 같은 적에게 한 번만 피해를 준다. 화면 밖 멀리 나간 탄환만 영역 안으로 되돌린다.
실제 최대 강화 무기의 발사량/DPS를 재현한 밸런스 테스트는 아니다.

모든 조건에서 게임오버 없이 적 620마리와 요청한 탄환 수가 유지됐다. 기존 main 구간
계측값은 계속 약 3–4ms였지만, 실제 틱 간격은 크게 증가했다. 기존 계측에서 빠지는
투사체/다른 콜백 비용이 실제 런에서도 중요하다는 것을 확인했다.

## 4. 렌더링 분리 측정

빈 화면에 실제 star/ember 탄환을 절반씩 표시하고 위치와 회전을 계속 바꿨다.
이동 물리/충돌 조회는 끈 상태이며 캐시된 그리기 명령을 사용한다.

| 탄환 수 | 글로우 | 화면 프레임 간격 평균 | p99 | 평균 draw calls |
|---|---|---:|---:|---:|
| 0 | 켬 | 0.62ms | 0.94ms | 0 |
| 500 | 켬 | 8.73ms | 16.02ms | 3,750 |
| 1,000 | 켬 | 17.59ms | 21.55ms | 7,500 |
| 2,000 | 켬 | 39.87ms | 49.24ms | 15,000 |
| 2,000 | 끔 | 26.46ms | 36.06ms | 11,000 |

이 시간에는 테스트의 트랜스폼 변경, 엔진과 드라이버, 렌더링이 포함된다. GPU-only
프로파일은 아니므로 GPU 자체가 포화됐다고 단정하지 않는다. CPU 분리 측정 시간과
이 표를 단순 합산해서 실제 게임 FPS를 계산해서도 안 된다.

현재 `CrowdRenderer`는 적과 적 탄환을 묶지만, 플레이어의 `HomingProjectile`은
각 노드에서 여러 polygon/circle을 그린다. 매 프레임 `queue_redraw()`가 없어도
그리기 호출은 유지된다. 글로우를 꺼도 2,000개에서 11,000회가 남았다.

실행 로그에는 `2D MSAA is not yet supported for GLES3` 경고가 있었다.
현재 측정에서 MSAA 설정 변경을 해결책으로 검증한 것은 아니다.

## 권장 후속 작업

1. **충돌 조회부터 개선:** 단발/관통 탄환에 맞춰 필요한 명중 수에서 멈추는 조회,
   조회 버퍼 재사용, 투사체용 더 작은 셀을 실험한다. 적 군중 분리용 192px 셀까지
   일괄 변경하지 말고 별도 A/B 측정한다. 대상 순서, 큰 적의 반지름, 관통 명중 누락을 검증한다.
2. **재탐색 폭주 방지:** 가까운 셀부터 탐색하고 남은 셀에서 더 가까운 표적이 나올 수 없으면
   종료하는 방식부터 검토한다. 재탐색을 여러 틱에 분산한다면 유도 반응 지연도 검증한다.
3. **플레이어 투사체도 배치 렌더링:** star/ember 본체를 아틀라스에 준비하고 몸체/글로우를
   MultiMesh 등으로 묶는 실험을 한다. 현재 적용된 적 렌더러와 투사체 그림 경로는 다르다.
4. **반납 경로 개선:** 활성 인덱스를 사용한 swap-remove와 풀 포함 여부 플래그를 검토한다.
   실행 중 활성 배열 순회와 반납이 겹치는 경우, 중복 반납 방지도 확인한다.

후속 변경 전후에는 같은 시드와 조건으로 아래 테스트를 순차 실행한다. 실제 플레이의
투사체 최고 개수, 후반 강화 조합, 릴리스 빌드 및 전체 화면+게임 통합 렌더링은 추가 검증 대상으로 남는다.

powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_projectile_performance.ps1 -Mode baseline
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_projectile_performance.ps1 -Mode cpu
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_projectile_performance.ps1 -Mode integration

60FPS 달성을 뜻하지 않는다. 실행기는 스크립트 오류와 완료 마커 누락, 제한 시간 초과도 검사한다.
