# 성능 — 원인 분석과 적용 (2026-09-19)

측정 환경: Godot 4.7.2, GLES3(Compatibility), 1280×720 창모드, RTX 5060 Ti, vsync 끔.
측정 도구는 `tests/perf_bench_capture.gd`(스위트 밖, 직접 실행)와 인게임 `F10 → F11` 패널입니다.

```powershell
godot --path . --script res://tests/perf_bench_capture.gd
$env:BENCH_LAYERS = "1"      # 정지 장면에서 레이어별 렌더 비용 분해
$env:BENCH_DISABLE = "milk"  # numbers, lights, weapons, milk, fields … 끄고 A/B
```

벤치 장면은 불만이 실제로 나오는 순간을 재현합니다 — 적 동시 상한 620마리, 두 생존자가 **실제
강화 경로로** 레벨 12까지 키운 진화 무기 넷씩, 공격 보물 넷을 최대로. 숫자를 사전에 직접 써넣지
않고 `_apply_upgrade`로 만들기 때문에, 밸런스가 바뀌면 벤치도 따라 바뀝니다.

## 1. 무엇이 틀렸었나 — 이전 분석의 정정

지난번 문서는 "이펙트 노드 각자의 `_physics_process`가 틱당 8~10ms"라고 적었습니다. 절반만 맞았습니다.

- **투사체는 이미 노드별로 돌지 않았습니다.** `WeaponController`가 한 루프에서 전부 스텝하고
  `ProjectileRenderer`가 MultiMesh로 그립니다. 틱당 0.2ms였습니다.
- 스크립트 콜백을 전부 계측해도(`FrameProbe`) 틱당 약 8ms였는데, 실제 틱은 17.5ms였습니다.
  나머지는 **스크립트가 끝난 뒤 엔진이 하는 일**이었고, 그 정체는 둘이었습니다.
  1. `queue_redraw()`는 지연 호출입니다. 실제 `_draw()`는 틱 뒤 메시지 큐 플러시에서 돌기
     때문에 어떤 스크립트 타이머에도 잡히지 않았습니다.
  2. `add_theme_color_override`는 **같은 색이어도** 테마 변경을 알리고, 라벨은 그때 텍스트를
     통째로 다시 셰이핑합니다(한글, HarfBuzz). HUD가 이걸 매 틱 수십 번 했습니다.
- 그리고 모든 비용에 곱해지는 배수가 있었습니다: 한 프레임이 16.7ms를 넘으면 Godot는 다음
  프레임에 밀린 물리를 최대 8번 몰아서 돌립니다. 틱 하나가 17.5ms였으므로 프레임마다 8틱
  = 140ms. **죽음의 나선**이었습니다. 틱 비용을 예산 아래로 내리자 나선이 풀리면서 개선이
  곱절로 돌아왔습니다.

## 2. 적용한 것

### 캐싱 — 바뀌지 않은 것을 다시 계산하지 않기

| 대상 | 전 | 후 |
|---|---|---|
| HUD 테마 색·스타일박스 색·툴팁 (`ui_write.gd`) | 매 틱 무조건 대입 → 재셰이핑 | 값이 바뀔 때만 대입 |
| HUD 레이아웃 (`player_perspective.hud`) | 매 틱 막대·초상화·칸 재배치 | 시점이 바뀔 때만 |
| 장비 칸 쿨다운 링 (`equipment_border.gd`) | 16개가 매 프레임 재그리기, AA 선 96개씩 | 링 모양이 바뀔 때만, 폴리라인 1~2개, 점 좌표 캐시 |
| 우유 웅덩이 | 매 틱 26각형+윤곽+원 7개 재생성 | 한 번 그리고 퍼짐=`scale`, 페이드=`modulate` |
| 궤도 장판 | 매 틱 재그리기 | 한 번 그리고 `rotation`으로 회전 |
| 냉기 오라 | 72·64각형 원판(매번 삼각분할)까지 매 틱 | 원판은 한 번, 움직이는 호만 자식 캔버스에서 |
| 피격 섬광 (`combat_flare.gd`) | 본체+글로우 매 프레임 재그리기 | 재그리기 없음(변환만) |
| 피격 사운드 이름 | 히트마다 `"impact_" + family` 문자열 생성 | 무기별 캐시 |

HUD 캐싱 하나만으로 152 → 43ms였습니다. 가장 큰 단일 원인입니다.

### 배칭 / 드로우 콜 축소

- **우유 웅덩이 → `MilkPoolRenderer`**: 웅덩이 노드는 판정·수명·조명만 맡고, 그리기는
  MultiMesh 쿼드 한 장 × 웅덩이 수 = **드로우 콜 1회**. 모양(흔들리는 테두리·채움·코어·물방울)은
  프래그먼트 셰이더가 해석적으로 계산하고 `fwidth`로 안티앨리어싱합니다. 원본 26각형보다 오히려
  매끈합니다. 무기 레이어 드로우 690 → 302.
- **`BatchPaint`**: 채운 도형은 전부 `canvas_item_add_triangle_array` 한 번(떨어진 삼각형도
  한 명령), 선은 색·두께별 `draw_multiline` 한 번. 지뢰 하나 **33 → 3회**(최대 20개),
  궤도 장판 파편당 4명령 → 전체 5명령.
- **사슬**: 고리 30개 × AA 폴리라인 4개 = 120명령 → 층별 `draw_multiline` 8회. **112 → 5회**.
- **데미지 숫자 → `DamageNumberField`**: 숫자마다 Label+Tween을 만들고 지우던 것(초당 최대
  480노드)을 링 버퍼 하나 + `draw_string`으로. `Font`의 셰이핑 캐시 덕에 같은 숫자는 다시
  셰이핑되지 않습니다.

### 투명 오버드로우 / GPU 비용

- **부차 조명 예산**: 웅덩이마다 붙던 에너지 0.09짜리 바닥 조명이 30개. 2D 조명은 닿는 모든
  픽셀의 셰이더 루프를 늘리므로 31개 조명만으로 0.74ms였습니다. `LightField.attach(minor=true)`에
  전역 6개 예산 → 7개, 0.15ms. 냉기 오라·중력장 같은 중요한 조명은 제한하지 않습니다.
- **웅덩이 셰이더**: 쿼드 모서리(테두리가 닿지 않는 21%)는 삼각함수 전에 `discard`, 물방울
  루프는 0.62~0.82 띠 안에서만. 30장이 크게 겹치는 게 웅덩이의 본성이라 싼 픽셀이 중요합니다.
- **모서리 분할**: 모든 스타일박스가 반지름과 무관하게 `corner_detail = 12`. 7px 모서리에
  12분할은 과해서, 반지름 × 0.6(오차 0.1px 미만)으로 → HUD 패널 프리미티브 1.53만 → 1.08만.
- **스파크 요청**: 틱당 120개 → 24개. 필드는 260개까지만 살고 수명이 0.2~0.3초라, 틱당 20개를
  넘는 요청은 생기자마자 화면의 스파크를 밀어낼 뿐이었습니다.

### 공간 질의

`EnemySpatialGrid.query_radius`가 192px 거친 셀을 돌며 셀 안 **모든 적 노드**의 속성을 읽었습니다.
밀집 군중에서 셀 하나에 100마리가 넘으니, 반경 34px 궤도 파편 질의 하나가 수백 노드를 훑었습니다.
이미 있던 48px 세밀 격자와 패킹된 위치 배열로 먼저 거르고, 통과한 것만 노드를 읽습니다(최종 판정은
여전히 실제 위치). 궤도 장판 0.95 → 0.24ms, 장판·웅덩이·지뢰·중력 모든 호출자가 함께 빨라졌습니다.
전수 검사와 결과가 같다는 것을 `render_budget_test`가 무작위 질의 60개로 확인합니다.

## 3. 적용하지 않은 것과 이유

- **`max_physics_steps_per_frame` 낮추기**: 나선의 안전장치로 유효하지만, 과부하 시 게임이
  슬로모션이 되는 대가가 있습니다. 틱 비용 자체를 예산 아래로 내렸으므로 현재 벤치에선 발동할
  일이 없습니다. 더 약한 기기에서 나선이 다시 보이면 가장 먼저 검토할 스위치입니다.
- **HUD 드로우 콜(약 170회)**: 칸 패널·아이콘·글자 순서를 바꿔 배치를 합치려 했지만, 이
  렌더러는 캔버스 아이템 사이를 합치지 않아서 효과가 없었고 되돌렸습니다. 줄이려면 칸 16개를
  컨트롤 하나의 `_draw`로 합쳐야 합니다. 렌더 0.6ms라 우선순위를 낮췄습니다.
- **적 AI · 군중 분리 · 격자 재구축(틱당 약 2.5ms)**: 이미 배치·분할·패킹돼 있고 적 수에
  선형입니다. 남은 것 중 가장 크지만, 다음 한 단계는 GDScript 밖(GDExtension)이 될 겁니다.
- **월드 오프스크린 버퍼(현재 2518×1652)**: 원근 투영의 화질을 위한 슈퍼샘플이라 건드리지
  않았습니다. 해상도가 더 큰 창에서 오버드로우가 문제되면 `SUPERSAMPLE`이 레버입니다.

## 4. 도구

- **`FrameProbe`**(`scripts/systems/frame_probe.gd`): 어떤 스크립트든 구간을 보고할 수 있는
  정적 누산기. 꺼져 있으면 호출 지점마다 bool 하나. 모든 `_draw`, 이펙트 노드의 틱, 피격 경로가
  보고합니다.
- **F11 패널**: main 구간 막대 아래에 **노드별(틱당)** 상위 8개가 나옵니다 — 이전엔 "이펙트
  노드 등 그 외"라는 한 줄로만 보이던 부분입니다.
- **벤치 단계 분해**: 엔진 신호(`physics_frame`, `process_frame`, `frame_pre_draw/post_draw`)와
  물리 우선순위 최상·최하 마커 노드로 한 프레임을 [스크립트 / 엔진 꼬리 / _process / 렌더 제출]로
  나누고, 프레임당 물리 틱 수 분포를 찍습니다. 이번 조사의 핵심 단서(엔진 꼬리)는 이것으로
  찾았습니다.
