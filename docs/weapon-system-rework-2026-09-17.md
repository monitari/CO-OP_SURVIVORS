# 무기 성장·진화·공명 개편 — Phase 1·2

2026-09-17. 개편안 §25의 Phase 1(유저 경험)과 Phase 2(유지보수)를 적용한 기록입니다.
Phase 3(공명 재구축)의 일부 — 일반 공명 템플릿 — 은 앞당겨 들어갔고, 그 이유는 아래
[템플릿을 앞당긴 이유](#템플릿을-앞당긴-이유)에 있습니다. Phase 4(밸런스·성능)는 남아
있습니다.

---

## 한 줄로

규칙을 네 문장으로 줄이고, 그 네 문장이 깨지지 않는지를 테스트가 대신 지키게 했습니다.

```
Lv.3에 방향을 고른다.
Lv.7에 자동으로 진화한다.
진화 무기 두 개의 태그가 맞으면 공명 후보가 생긴다.
보스를 잡으면 공명핵으로 그중 하나를 고른다.
```

## Phase 1 — 유저 경험

### 진화 조건은 무기 레벨 7 하나

예전 조건은 `무기 Lv.7` **그리고** `Lv.3에 고른 테크가 지정하는 보물 Lv.4`였습니다.
문제는 난이도가 아니라 **정보의 순서**였습니다 — 여섯 레벨 뒤의 요구 조건을 Lv.3 카드가
결정하는데, 그 요구 조건은 결정하는 시점에 화면 어디에도 없었습니다. 실패 양상은 "어렵다"가
아니라 "무기가 왜 멈췄는지 모른다"였습니다.

- `EvolutionCatalog.REQUIRED_TREASURE_TIER` 삭제
- `_available_evolution`은 `tier >= EVOLUTION_TIER`만 확인
- 보물은 진화 열쇠에서 **시너지**로 (§9)

### 진화는 카드가 아니라 사건

`evolve_weapon` 카드를 없애고, 레벨 7에 닿는 순간 `_apply_pending_evolutions`가 그 자리에서
진화시킵니다. "이미 값을 다 치른 것을 이제 사시겠습니까"는 선택이 아니라 전원이 매번 집는
카드였고, 그 카드가 실제로 저울질할 수 있는 카드의 자리를 하나 차지하고 있었습니다.

### 성장 100% 계승

`WeaponGrowth.EVOLUTION_CARRY = 0.35`를 삭제했습니다. 진화 무기는 기본 무기가 도달했던
**배수 그대로** 자기 카탈로그 수치에서 출발합니다. 예전에는 트리가 보상하는 바로 그 순간
그때까지 산 화력 카드의 3분의 2가 증발했고, 그 사실을 알려주는 화면은 없었습니다. 보이지
않는 변환율은 메커니즘이 아니라 세금입니다.

### 공명핵

태그가 맞으면 켜지던 것을 없앴습니다. 공명이 두 사람이 이미 읽고 있던 메뉴 위에 배너 한
줄로 도착했고, 가능한 공명이 둘일 때 어느 쪽을 원하는지 말할 방법이 없었습니다.

| | 예전 | 지금 |
|---|---|---|
| 조건 | 태그 일치 → 즉시 활성 | 태그 일치 → `공명 가능` 알림만 |
| 활성화 | 레벨업 중 자동 | **보스 1·2 격파 → 공명핵 → 선택** |
| 슬롯 | 3 | **2** (= 런이 주는 핵 개수) |
| 선택 화면 | 없음 | **후보가 둘 이상일 때만** (§13) |

핵에는 종류가 없습니다. `화염용`·`냉기용`을 만들면 빌드 완성이 다시 주사위에 묶입니다.
쓸 수 있는 후보가 없으면 핵은 보관되고, 그렇다고 알려줍니다 — 조용히 아무 일도 하지 않는
보상이 이 시스템이 없애려던 실패 양상 그 자체입니다.

슬롯 수(2)와 런이 주는 핵 수(2)를 같게 둔 것은 의도한 것입니다. "공명은 몇 개까지?"의 답이
규칙이 아니라 두 사람이 직접 본 사건이 됩니다.

## Phase 2 — 유지보수

### 테크는 전부 같은 모양

| | 성격 | 항상 특화하는 축 | 고유 축 |
|---|---|---|---|
| **A** | 강한 한 방 · 화력형 | `weapon_power` | 고유 A/B 중 하나 |
| **B** | 빠른 반복 · 수량/속도형 | `weapon_rate` | 나머지 하나 |

균형형 테크 다섯 개(성좌 설계 · 화염 성운 · 월식 · 지평 광선 · 추적 놀이)를 없앴습니다.
전부 네 축을 고르게 올리는 "고르게 완성합니다" 계열이었고, 아무것도 특화하지 않는 선택지는
방향이 아니라 안전해 보이는 기본값입니다. 대신 사슬에 **팽팽한 사슬**(약한 파동 두 번)을
더해, 테크가 하나뿐이라 자동으로 정해지던 유일한 무기도 이제 묻습니다.

`focus()`는 이제 두 값뿐입니다 — 특화 축 **1.30**, 나머지 **0.75**.

### Primitive

고유 강화 24개 전부에 `primitive` 이름을 붙였습니다(`Count` · `Range` · `Radius` ·
`ProjectileSpeed` · `Pierce` · `Chain` · `Slow` · `Force` · `Area`). 무기별 전용 강화 계산
함수는 없고, 검증 테스트가 목록에 없는 이름을 거부합니다.

### 태그 2개

진화 무기는 **속성 1 + 행동 1**을 갖습니다. 두 목록은 겹치지 않습니다 — 뇌전은 속성이고,
폭풍은 그 속성이 바닥을 덮는 방식입니다. 예전에는 네 개씩이라 거의 모든 조합이 뭔가에
걸렸고, 공명이 빌드의 결과가 아니라 슬롯머신처럼 읽혔습니다.

| 무기 | 속성 | 행동 | | 무기 | 속성 | 행동 |
|---|---|---|---|---|---|---|
| 성좌 관통포 | arcane | pierce | | 천구 의식 | arcane | aura |
| 뇌신의 격노 | lightning | storm | | 심판의 창 | holy | projectile |
| 초신성 | fire | explosion | | 파멸의 정원 | shadow | control |
| 절대영도 | frost | aura | | 물수제비 물고기 | frost | tracking |
| 흑월참 | shadow | melee | | 크림 해일 | frost | control |
| 성흔의 사슬 | holy | chain | | 사건의 지평선 | arcane | storm |

기본 무기의 태그도 2개로 줄였습니다.

### 내부 ID

표시 이름과 내부 ID를 분리했습니다 — `TECH_COMET_TRACKING`,
`EVOLUTION_CONSTELLATION_CANNON`, `RESONANCE_THERMAL_FRACTURE`. 테크·진화·공명이 **하나의
네임스페이스**를 공유하며, 검증 테스트가 전역 중복을 거부합니다. 실제로 이 검사가 하나를
잡았습니다: 공명 `absolute_zero`가 진화 무기 `absolute_zero`와 같은 id였습니다(→
`glacial_prison` 빙하 감옥).

### 자동 검증 — `tests/weapon_data_test.gd`

§21의 목록을 기계 검사로 옮겼습니다. 이 시스템이 유저에게 하는 약속은 전부 **모양**에 대한
약속인데 그중 무엇도 타입 시스템이 지켜주지 않고, 전부 서둘러 추가한 13번째 무기가 조용히
깨뜨리는 종류의 것입니다 — 무기는 동작하고, 런은 굴러가고, 78쌍 중 하나에 남은 게임 수명
내내 공명이 없습니다.

검사 항목: 테크 개수·역할·축 구성, 진화 존재·유일성·보물 게이트 부재·100% 계승, Primitive
이름, 태그 등록/개수/겹침/도달 가능성, 공명 요구 태그·중복 id·78쌍 커버리지·도달 불가능한
항목, 슬롯 수, 전역 쿨다운 배율 부재, 내부 ID 접두사와 중복.

## 템플릿을 앞당긴 이유

태그를 4개에서 2개로 줄이면 기존 25개 공명의 요구 태그를 전부 다시 매핑해야 하고, 78쌍
커버리지를 유지하려면 **손으로 쓴 공명이 41개**가 필요했습니다. `perform_resonance`는
resonance id에 대한 `match` 문이므로 그건 손으로 쓴 효과 16개를 새로 만든다는 뜻이었고,
Phase 3은 바로 그 16개를 지우는 작업입니다.

그래서 §15의 일반 공명 층을 Phase 2에 넣었습니다.

```
고유 공명 24   두 태그가 함께 특별한 뜻을 갖는 조합만 손으로
               (화염+냉기는 "냉기 장판에 화염 효과"가 아니라 열충격)
일반 공명 41   속성 × 행동에서 자동 생성 — 행동이 모양(템플릿 9종), 속성이 색과 부가 효과
```

처리 순서는 `고유 공명이 있으면 그것을, 없으면 템플릿을`입니다.

**커버리지가 구조적으로 보장됩니다.** 카탈로그를 진화 로스터에서 생성하므로, 진화 무기 A와
B는 항상 A의 속성과 B의 행동을 공급하고, 두 태그 목록이 겹치지 않으니 둘은 반드시 다르며,
양쪽이 각각 하나씩 낸 것이 됩니다. 13번째 무기는 태그 두 개만 주면 기존 12개 전부와 이미
공명합니다. 짝당 후보 수는 1~4개(평균 2.3)로, 선택 화면에 올리기 적당한 크기입니다.

템플릿 9종: `barrage` · `lance` · `cleave` · `conduit` · `field` · `bombard` · `snare` ·
`blast` · `tempest`. 속성 부가 효과 6종: 화염(연소) · 냉기(둔화) · 뇌전(연쇄) ·
비전(인력) · 그림자(처형) · 성흔(회복 + 적 탄 제거). 생성된 설명문은 실제로 적용되는 부가
효과와 **같은 문구**에서 만들어지므로 텍스트와 효과가 어긋날 수 없습니다(§20).

### 공명별 쿨다운 (§16)

활성화할 때 전체에 곱해지던 `× 0.78`을 없앴습니다. 카탈로그가 말하는 값과 게임이 쓰는 값이
달랐으므로, 카탈로그의 숫자는 유저에게 보여줄 수 없는 숫자였습니다. 기존 24개는 그 배율을
이미 반영한 값으로 다시 적었습니다(예: 6.0 → 4.7).

## 검사 결과

헤드리스 스위트 **63종 중 61종 통과**. 통과하지 않는 넷(`projectile_performance`와
`online_peer_probe` 포함)은 전부 **개편 전에도 같은 상태**였고, 각각을 개편 전 코드로 다시
돌려 확인했습니다.

| | 상태 | 확인 |
|---|---|---|
| `pressure_soak_test` | 실패 | 계측기. 개편 전 29.3s / 개편 후 27.3s (기준 40s) — 아래 참조 |
| `coop_soak_test` | 판정선 위아래 | 기준 14.0s, 측정 13.6~14.2s. 개편 전 코드도 13.8s로 실패 |
| `projectile_performance_test` | 실패 | 개편 전 코드에서 **같은 네 줄**이 그대로 실패 |
| `online_peer_probe.gd` | 실행 불가 | `--peer-mode=host\|client` 인자가 필요한 두 프로세스 도구 |

`coop_soak_test`의 기준선이 현재 페이스와 너무 가까워서, 같은 코드로 돌려도 통과하는 판과
13.6s로 떨어지는 판이 섞입니다. `rooftop_prototype_test`는 `_PASS` 대신 `ROOFTOP25 OK`를
찍으므로 스위트 집계 스크립트에서 빈칸으로 보일 수 있습니다(정상 통과).

### 지나가다 고친 불안정 검사 둘

개편과 무관하지만, 이 작업의 회귀로 오해받을 자리라 같이 고쳤습니다.

- **`dash_test`** — 무적이 끝난 뒤 피해가 들어가는지 보는 검사가 `hurt()`를 그냥 불렀는데,
  라이라의 **회피 6%**가 뜨면 `hurt()`가 `false`를 돌려주어 열여섯 판에 한 번쯤 빨간불이
  났습니다. 대시와 아무 상관없는 주사위였으므로 `can_dodge = false`로 고정했습니다.
- **`level_up_card_test`** — "확정하면 강화가 적용된다"를 플레이어 능력치 아홉 개로만
  확인하고 있어서, 두 사람이 마침 치명·회피·관통·지속 계열 보물을 집은 판은 "아무 일도
  안 일어났다"로 읽혔습니다. 속성 목록은 완전해질 수 없으므로 **로드아웃 자체**(무기 레벨 +
  보물 id/레벨)를 스냅샷에 넣어 구조적으로 닫았습니다 — 어떤 카드든 둘 중 하나는 반드시
  바꿉니다. 25판 연속 통과 확인.

`equipment_border`의 `resonating`도 되살렸습니다. 직전 커밋이 공명의 무기 침묵을 없애면서
같이 지웠는데 `combat_readability_test`가 아직 그걸 보고 있었고, §17의 "공명 슬롯 점유 여부"는
실제로 필요한 정보라 **쿨다운 고리는 그대로 두고 금색 표시만** 복구했습니다.

### 밸런스 신호

개편 전후를 같은 방식으로 재서 붙입니다. 둘 다 **개편 전에도 이미 기준선 아래**였고, 이
작업이 만든 회귀가 아닙니다.

| 계측 | 개편 전 | 개편 후 | 판정 기준 |
|---|---:|---:|---:|
| `coop_soak` 레벨 간격 | 13.8s | 13.6s ~ 14.2s (실행마다 흔들림) | ≥ 14.0s |
| `pressure_soak` 생존 | 29.3s | 27.3s | ≥ 40s |
| `pressure_soak` 첫 다운 | 22.0s | 22.0s | ≥ 35s |
| `pressure_soak` 처치 | 17 | 14 | ≥ 20 |

`pressure_soak`이 재는 구간은 **런 시작 30초**, 즉 레벨 3에도 닿기 전이므로 진화·공명 변경과는
무관합니다. 움직인 이유는 보물 쪽입니다 — 진화 게이트가 사라지면서 "테크 필수 보물을 위해
발견을 배급하던" 규칙도 같이 없앴고, 그 결과 무인 조작 한 쌍의 초반 보물 선택이 달라졌습니다.
`_fusion_path_value`의 가중치도 관문(최대 +114)에서 시너지(최대 +38)로 낮췄습니다.

이 값들이 맞는 난이도인지는 Phase 4의 질문입니다. 여기서는 **바뀌었다는 사실과 크기만**
기록합니다.
